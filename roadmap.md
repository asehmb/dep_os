## Phase 1: Complete the Memory Subsystem

You just entered the higher half using temporary, coarse-grained assembly tables. Your first goal is to hand memory management over to a robust C implementation.

1. **Save the DTB Pointer:** QEMU passes the physical address of the Device Tree Blob (DTB) in register `x0` at boot. Before your boot assembly clobbers `x0`, save it to a global variable. You will need it to detect RAM size dynamically.
2. **Rebuild Tables in C:** Use your `setup_tables()` C function to build fine-grained (4KB or 2MB) L0-L3 tables in RAM.
3. **Swap to the C Tables:** Write the address of your new C-built L0 table into `TTBR1_EL1`.
4. **Tear Down the Lower Half:** Write `0` to `TTBR0_EL1` to destroy the identity map. Flush the TLB with `tlbi vmalle1is` and execute `dsb ish` / `isb`. From this moment on, any attempt to access a `0x4000...` physical address directly will correctly trigger a page fault.
5. **Physical Memory Manager (PMM):** Parse the DTB to find the exact start and end of physical RAM. Implement a page frame allocator (a bitmap or free-list) to track which 4KB physical frames are free or used.
6. **Kernel Heap (`kmalloc`):** Implement a dynamic allocator (like a bump allocator for early boot, followed by a slab or block allocator) backed by your PMM and VMM, so you can dynamically allocate lists, device structs, and thread control blocks.

## Phase 2: Bulletproof Debugging

Before writing complex hardware drivers, ensure you can catch your own mistakes.

1. **Robust Exception Handler:** Expand your `vectors.S` to route all Synchronous Exceptions (page faults, undefined instructions) to a C function.
2. **Decode Memory Faults:** In your C fault handler, parse `ESR_EL1` (Exception Syndrome Register). If it is a Data Abort (0x24) or Instruction Abort (0x20/0x21), print the exact faulting virtual address from `FAR_EL1`. This will save you weeks of debugging when your pointers inevitably break.

## Phase 3: Hardware Interrupts

Transition from software exceptions to asynchronous hardware events.

1. **Initialize the GIC (Generic Interrupt Controller):** Map the GICv2 or GICv3 MMIO regions into your higher-half virtual memory. Configure the GIC Distributor to route interrupts to your specific CPU core.
2. **Enable Interrupts:** Set up a hardware IRQ vector in your exception table. Unmask interrupts by clearing the `I` bit in the `daif` register (`msr daifclr, #2`).

## Phase 4: Time and Multitasking

Your kernel currently executes a single linear path. Multitasking requires time-slicing.

1. **ARM Generic Timer:** Program the architectural timer. Set an interval in `CNTP_TVAL_EL0`, enable it via `CNTP_CTL_EL0`, and route its specific IRQ number (usually PPI 30) through the GIC. Confirm you receive a timer interrupt every few milliseconds.
2. **Context Switching:** Write assembly logic to save the CPU state of a running task. You must push registers `x0`-`x30`, the program counter (`ELR_EL1`), and the processor state (`SPSR_EL1`) to the current task's stack.
3. **Kernel Scheduler:** Create a Thread Control Block (TCB) struct. Write a scheduler that intercepts the timer interrupt, saves the current thread's context, swaps the `SP_EL1` stack pointer to the next thread, and restores its registers.

## Phase 5: User Space (EL0)

Protect the kernel from buggy or malicious application code.

1. **User Page Tables:** When spawning a user thread, create a fresh page table hierarchy and load it into `TTBR0_EL1`. Set the page descriptors to allow unprivileged (EL0) execution and data access.
2. **System Calls (SVC):** Implement an exception handler for the `svc` instruction. When user code wants to print to the screen or allocate memory, it triggers `svc`, trapping back into EL1 where the kernel safely validates the request.
3. **The EL0 Drop:** To execute an application, forge a return state. Set `SPSR_EL1` to EL0 mode, point `ELR_EL1` to the user binary's entry point, set `SP_EL0` to the user stack, and execute `eret`.

# Beyond User Space: The Userland & Desktop Roadmap

Congratulations on reaching Exception Level 0 (EL0). You have transitioned from writing a raw kernel to building an actual Operating System. From this point forward, the kernel’s job is to protect hardware and provide abstractions, while user space does the actual work.

Here is the sequential roadmap for building your userland, from the first file system to a graphical desktop environment.

---

## Phase 6: Storage and Block Devices

To run programs, you need to load them from a disk rather than hardcoding them into kernel memory.

1. **PCIe/PCI Bus Enumeration:** If you are using QEMU, the virtual disk is likely attached via PCIe. Write a driver to enumerate the PCI bus and find connected devices.
2. **Virtio-Block Driver:** Implement a driver for `virtio-blk` (standard in QEMU AArch64). This requires setting up Virtio Ring buffers (virtqueues) to send read/write requests to the host emulator.
3. **Block Device Abstraction:** Create a generic interface in your kernel (e.g., `block_read(device_id, sector, buffer)`). Your filesystem will talk to this layer, not the raw hardware.

## Phase 7: The Virtual File System (VFS)

The VFS is the abstraction layer that makes everything look like a file.

1. **VFS Core:** Implement the abstraction of `inodes` (files/directories), `dentries` (directory entries), and `superblocks` (mounted filesystems).
2. **FAT32 Implementation:** Start by implementing the FAT32 filesystem. It is relatively simple, well-documented, and the standard for UEFI boot partitions.
3. **File Syscalls:** Implement the core POSIX file system calls in your kernel: `open`, `read`, `write`, `close`, `seek`, and `readdir`.

## Phase 8: Executable Loading & The `init` Process

Now that you can read files from a disk, it is time to load dynamic programs.

1. **ELF Parser:** Write a parser that reads an Executable and Linkable Format (ELF) file from your VFS. It needs to iterate through the ELF Program Headers and map the `PT_LOAD` segments into EL0 virtual memory using your VMM.
2. **The `init` Process (PID 1):** Hardcode the kernel to load a specific file from the disk (e.g., `/bin/init`) on boot. This is the very first user-space process. If this process crashes, the kernel panics.
3. **Process Forking & Exec:** Implement the `fork()` syscall (to duplicate the current process) and `execve()` (to replace the current process with a new ELF binary).

## Phase 9: Input, Output, and the Terminal (TTY)

To interact with your OS, you need keyboards and screens abstracted into a terminal.

1. **Input Drivers:** Write a driver for `virtio-input` or emulate a PS/2 controller (PL050 on ARM) to read raw keyboard scancodes.
2. **The TTY Layer:** Create a terminal subsystem. It takes raw keyboard scancodes, translates them to ASCII/UTF-8, buffers them, and handles line-editing (like backspace).
3. **Standard I/O:** Map file descriptors `0` (stdin), `1` (stdout), and `2` (stderr) to your TTY device.
4. **The Shell:** Write a basic shell program in user space (e.g., `sh`). It should run in an infinite loop, read from stdin, parse commands, and use `fork()` + `execve()` to run other programs like `ls` or `cat`.

## Phase 10: Inter-Process Communication (IPC)

As you move toward a Desktop Environment, isolated programs need to talk to each other safely.

1. **Pipes:** Implement anonymous pipes (`|`), allowing the output of one process to flow directly into the input of another.
2. **Unix Domain Sockets / Shared Memory:** Implement a way for two processes to map the exact same physical page of RAM into their respective virtual address spaces for high-speed data transfer.
3. **Signals:** Implement basic POSIX signals (like `SIGINT` when you press Ctrl+C, or `SIGKILL` to force-terminate a buggy process).

## Phase 11: Graphics and the Display Environment (DE)

Moving from a text console to a pixel-driven graphical user interface.

1. **Framebuffer Driver:** Write a driver for `virtio-gpu` or `ramfb`. The hardware will give you a pointer to a chunk of memory. Writing a 32-bit hex value (ARGB) to this memory instantly turns a pixel that color on the screen.
2. **User-Space Graphics Server (Compositor):** Do not put window management in the kernel. Write a user-space daemon (similar to Wayland or X11) that owns the framebuffer.
3. **Window Management:** The Compositor uses IPC (Shared Memory) to let other user-space apps draw their own windows into hidden buffers. The Compositor then mathematically composites these overlapping windows onto the main framebuffer.
4. **Desktop Environment (DE):** Write client applications that talk to your Compositor:
   - A background wallpaper drawing app.
   - A taskbar/panel app.
   - A graphical terminal emulator that draws text fonts (like PC Screen Font) pixel-by-pixel into a window.

## Phase 12: Networking (Optional)

Connecting your OS to the outside world.

1. **NIC Driver:** Implement `virtio-net` to send and receive raw Ethernet frames.
2. **Network Stack:** Implement a user-space daemon or kernel subsystem to handle the OSI model: ARP, IPv4/IPv6, ICMP (ping), UDP, and eventually TCP.
3. **Sockets:** Expose the network to user programs via the BSD Socket API (`socket`, `bind`, `listen`, `accept`, `send`, `recv`).
